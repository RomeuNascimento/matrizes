# Revisão do projeto — 11/07/2026

Revisão completa do código-fonte (src/, tests/, configuração), com a suíte de
testes e o typecheck executados como base.

**Estado verificado:** 64/64 testes passando · `tsc --noEmit` limpo.

## Visão geral

O projeto está em ótimo estado para um MVP. Destaques:

- **Leitor de PES** portado com disciplina do pyembroidery e validado contra o
  oráculo em 37 arquivos reais — a parte mais arriscada do projeto é também a
  mais bem testada.
- **Arquitetura Electron correta**: `contextIsolation` ligado, `nodeIntegration`
  desligado, superfície mínima via `contextBridge`, CSP no `index.html`, e o
  renderer nunca toca disco/banco diretamente.
- **Banco sólido**: migrações versionadas, WAL, `foreign_keys` ligado, FTS5 com
  `remove_diacritics`, backup com `VACUUM INTO` + rotação.
- **Cópia segura** (`.part` → rename, checagem de espaço e de tamanho) e cache
  de miniaturas por hash com auto-cura são decisões de design muito boas.
- Código legível, bem comentado em português, com contratos compartilhados.

Os achados abaixo estão em ordem de importância.

## A. Bugs / comportamento incorreto

### A1. Mover ou renomear um arquivo duplica a matriz e perde a organização

`repository.religarArquivoMovido` e `findArquivoByHash` existem
(`src/main/db/repository.ts:115` e `:167`) mas **nunca são chamados**. O
importador (`src/main/services/importer.ts:106`) só procura por caminho: se a
usuária move `Natal/flor.pes` para `Páscoa/flor.pes` e reimporta:

1. uma **matriz nova** é criada para o caminho novo — favoritas, etiquetas,
   nome editado e status da matriz antiga **não acompanham**;
2. o registro antigo continua apontando para um caminho que não existe mais;
3. como os dois registros têm o mesmo hash, o par aparece na tela
   **“Repetidos” como “2 cópias idênticas”**, sendo que uma delas é fantasma.

Correção sugerida: quando `findArquivoByPath` falhar, procurar por
`findArquivoByHash` entre arquivos cujo caminho não foi visto na varredura
atual e religar com `religarArquivoMovido`.

### A2. A tela “Com problema” nunca esvazia

`erros_processamento.resolvido` só aparece no schema e no
`SELECT ... WHERE resolvido = 0` (`src/main/db/repository.ts:612`) — **nada
nunca grava `resolvido = 1`**. Se um arquivo falhou uma vez (ex.: pendrive
desconectou no meio da leitura) e depois foi importado com sucesso, ele fica
listado em “Com problema” para sempre. Além disso, cada reimportação com falha
insere uma linha nova, acumulando duplicatas do mesmo caminho.

Correção sugerida: ao processar um arquivo com sucesso, marcar como resolvidos
os erros pendentes daquele `caminho_absoluto` (e/ou deduplicar por caminho na
listagem).

### A3. Arquivos apagados nunca saem do catálogo

O importador reporta `removidos: 0` fixo (`src/main/services/importer.ts:179`).
Arquivos deletados do disco continuam na galeria com miniatura, e quebram só ao
“Abrir local”. Como a varredura já produz a lista completa de caminhos, dá para
detectar os ausentes (por pasta monitorada) e marcá-los (sugestão: um status
`ausente` em vez de apagar, para não perder organização por engano — ex.: HD
externo desconectado).

### A4. Nomes de arquivo entram no HTML sem escape (grade e detalhes)

O helper `esc()` existe (`src/renderer/app.ts:431`) mas a grade
(`app.ts:307-314`) e o painel de detalhes (`app.ts:519-529`) interpolam
`nomeExibido`, `caminhoAbsoluto` etc. direto em `innerHTML`. Um arquivo chamado
`flor <3 "azul".pes` quebra atributos `title`/`alt` e a renderização do card. A
CSP bloqueia script inline (não vira XSS executável), mas permite spoofing de
marcação (`img-src data:` está liberado) e corrompe a interface.

Correção: aplicar `esc()` em **toda** interpolação de dados vindos do banco,
como já é feito nas telas de manutenção.

### A5. Fechar a janela durante uma importação derruba o processo do handler

`mainWindow` nunca é zerado no evento `closed` (`src/main/index.ts:16`). Se a
janela for fechada com uma importação em andamento,
`ctx.getWindow()?.webContents.send(...)` (`src/main/ipc/register.ts:32`) acessa
uma janela destruída e lança “Object has been destroyed” dentro do callback de
progresso, abortando a importação no meio (o histórico fica `em_andamento`).

Correção: `mainWindow.on("closed", () => (mainWindow = null))` + checar
`win && !win.isDestroyed()` antes de `send`.

### A6. Erro na importação deixa a UI presa

`escolherEImportar` (`src/renderer/app.ts:133`) não tem try/catch: se o handler
IPC rejeitar, a barra de progresso fica visível para sempre e a usuária não
recebe nenhuma mensagem. Envolver em try/finally e mostrar um aviso amigável.

## B. Robustez / lacunas funcionais

- **B1. Miniaturas órfãs quando o conteúdo muda** — `atualizarConteudoArquivo`
  troca o hash, mas as linhas de `miniaturas` e os PNGs do hash antigo ficam no
  cache para sempre. Vale uma limpeza periódica (hashes sem arquivo
  correspondente).
- **B2. Importação sem trava nem cancelamento na UI** — o serviço já aceita
  `cancelado()` (`importer.ts:46`), mas a UI não expõe botão de cancelar, e
  nada impede duas importações simultâneas (dois cliques em “Adicionar pasta”).
- **B3. Grade limitada a 500 itens sem aviso** — `recarregar()` pede
  `{offset: 0, limite: 500}` fixo (`app.ts:275`). Com 3.000 matrizes, a
  contagem diz “3000 desenhos” mas só 500 aparecem, sem “carregar mais”. Para o
  público-alvo (milhares de matrizes) isso vai surgir cedo; sugestão: scroll
  infinito ou paginação simples.
- **B4. Validação de argumentos no IPC** — os handlers confiam nos tipos vindos
  do renderer (`register.ts`). Com contextIsolation o risco é baixo, mas como
  endurecimento barato vale validar (ex.: `Number.isInteger(id)`, caminho é
  string) antes de tocar banco/disco.
- **B5. Integridade do banco falha em silêncio** — `checarIntegridade` só faz
  `console.error` (`index.ts:58-60`). A usuária nunca vê; um `dialog.showErrorBox`
  orientando a restaurar backup seria mais fiel ao requisito “nunca perder a
  organização”.

## C. Qualidade / manutenção

- **C1. Tipos `any` no repositório** — `listarMatrizes`, `obterDetalhes`,
  `listarCategorias` etc. retornam `any` embora `src/shared/contracts.ts`
  defina os tipos. Tipar os retornos pegaria em compilação divergências como o
  mix de `snake_case`/`camelCase` que o renderer consome hoje
  (`d.nome_exibido` vs `d.larguraMm` em `app.ts:520-528`).
- **C2. `electron-builder` não está nas devDependencies** — `npm run dist`
  falha num clone limpo (o README até avisa; melhor simplesmente adicioná-lo).
- **C3. Modos de conflito `pular`/`substituir` sem UI** — o copier suporta três
  modos, mas o renderer sempre envia `"renomear"` (`app.ts:597`). Ou expor a
  escolha, ou remover a opção do contrato até existir UI.
- **C4. Electron 33** — funciona, mas está algumas majors atrás; planejar
  atualização periódica (segurança do Chromium embutido).
- **C5. Testes** — a base (parser/banco/pipeline/cópia) está muito bem coberta.
  Faltam testes para os cenários dos bugs A1–A3 (mover arquivo, erro que se
  resolve, arquivo apagado) — bons candidatos a acompanhar as correções.

## Prioridades sugeridas
